# Module 8 — Simulation Template Gallery

## 1. Purpose
Gives a brand-new user a working example to start from instead of a blank canvas
— pick a domain, click a scenario, and a complete pre-built graph (with realistic
parameters) loads onto the canvas. Directly supports the synopsis's "click to
pre-populate canvas" description (Section 5, Module 8) and its target-user goal of
being usable by a first-year student with zero simulation background.

## 2. Files owned by this module
| File | Role |
|---|---|
| `src/lib/simulation/simTypeRegistry.ts` (682 lines) | Defines every domain's `subScenarios: StarterGraph[]` — the actual starter-graph data (nodes, positions, params, edges) this module presents |
| `src/components/workspace/NodePalette.tsx` | **Also** the UI that renders these scenarios as clickable "SCENARIOS" buttons — see gap below |

## 3. ⚠️ Structural note: this is not a separate screen
The synopsis lists Template Gallery as module #8, implying a distinct UI surface.
In the actual code, there is no separate gallery page/screen at all — the starter
scenarios are rendered as a small "SCENARIOS" section at the top of the
**Node Palette sidebar** (Module 3), directly above the draggable node list, using
the exact same `subScenarios` data. Clicking a scenario button calls
`onLoadScenario(starter)` (defined in the workspace page), which converts the
`StarterGraph` into React Flow `nodes`/`edges` via `starterToRfNodes()` and
replaces the canvas contents outright (also stopping any running simulation).

This isn't necessarily wrong — it's a reasonable, space-efficient UI choice for a
three-panel workspace layout — but for documentation/grading purposes it's
important to be accurate: **Module 8 originally existed as data + a small UI section inside
Module 3's component, not as its own module-level screen.** 

**Rebuild Decision (Option B):** We have chosen to decouple the Template Gallery into a genuinely separate standalone overlay component (`TemplateGallery.tsx`). This overlay is triggered strictly when `nodes.length === 0` (an empty canvas). This structurally fulfills the synopsis's module boundary better and provides a clearer, less-cramped UX for first-time users.

## 4. Algorithm / logic
- Each of the 6 `SimTypeConfig` entries in the registry defines 2–3
  `subScenarios`: typically two realistic pre-built examples (e.g. Human Queue
  domain: "Bank Tellers" — 3 parallel teller resources; "ER Triage" — a decision
  node splitting patients into Critical Care vs Minor Treatment paths with
  different service-time distributions) plus one "Start from scratch" entry with
  an empty `nodes: []` array.
- `NodePalette.tsx` filters out the empty "Start from scratch" entry
  (`.filter(s => s.nodes.length > 0)`) before rendering the scenario list — a
  blank canvas is simply what a user gets by not clicking any scenario, so this
  placeholder entry is effectively a no-op in the UI today.
- Each `StarterGraph` node includes an explicit `position: {x, y}` — these are
  hand-placed layout coordinates per scenario, not auto-generated by the `dagre`
  layout library (which exists in the dependency tree but isn't invoked here).

## 5. Design notes for the rebuild
- Preserve every starter graph's nodes, edges, and parameter values exactly — they
  encode real domain expertise (realistic arrival rates, service-time
  distributions) that took thought to construct; changing a single number would
  be a logic/content change requiring the same explicit-flagging rule as a bug fix.
- Restyle scenario buttons using `.card-surface` with domain-appropriate node-type
  accent coloring instead of the neon cyan hover glow.
- Since we chose structural option (b) from Section 3 (a separate screen), we will
  surface each scenario's `description` text more prominently (currently a small subtext line).

## 6. Connections to other modules
- **Visual Graph Editor (Module 3)**: shares its host component (`NodePalette`)
  and calls straight into the workspace's `setNodes`/`setEdges`, same as manual
  editing and AI generation.
- **Simulation Engine (Module 5)**: every starter graph's node `params` must stay
  valid against that module's `*Params` interfaces — since starter graphs are
  hand-authored JSON (not generated), a future engine type change could silently
  desync them; worth a validation pass if `types.ts` changes during the rebuild.
- **Project Management (Module 2)**: the domain (`sim_type`) chosen at project
  creation time is what determines which of the 6 registries' `subScenarios` this
  module can offer for a given project — it's fixed per-project, not switchable
  later (there is no "change simulation type" UI either — see Module 10's synopsis
  promise of exactly that setting, not yet implemented).

## 7. Database tables touched
None — starter graphs are static, bundled data (`simTypeRegistry.ts`), not stored
per-user. They only touch the database indirectly once loaded onto a canvas and
auto-saved as that project's `graph_json` (Module 2).
